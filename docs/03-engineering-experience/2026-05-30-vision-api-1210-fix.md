# 2026-05-30 图片识别 400/1210 排查与修复

## 问题

学生端 `/question/ai-analyze` 图片识别功能重构后调用智谱 GLM-4V API 报 `400 BAD_REQUEST code=1210`（参数格式错误）。

## 背景

旧版图片识别代码在 `QuestionServiceImpl` 里硬编码了完整的 API 调用，用 `@Value` 注入明文密钥，直接调智谱 `glm-4.6v` 模型。重构时把这条调用链委托给了 `AnalysisService`，接入数据库密钥管理系统。

## 排查过程

### 第一轮：消息结构问题

对比旧版能用的代码和重构后的代码，发现 `callAiApiWithImage` 把 system prompt 和 user prompt 合并成了单一 user message，且 image_url 和 text 顺序颠倒。

查智谱官方文档发现 **GLM-4V 系列只支持 `user` 和 `assistant` 两种 role，不支持 `system`**。旧代码用 `glm-4.6v` 时有 system message 也能跑，是因为那个模型比较宽容。

修复：去掉 system message，把 system prompt 拼进 user content 的 text 里，消息结构改为只有 `role: "user"` 的单条消息。

结果：仍然报 1210。

### 第二轮：模型名问题

日志显示实际发出的 model 是 `glm-4v-flash`（`resolveVisionModel` 的默认值），而旧代码用的是 `glm-4.6v`。`glm-4v-flash` 是官方文档列出的免费视觉模型，但 `glm-4.6v-flash` 才是当前实际可用的模型标识。

修复：默认视觉模型从 `glm-4v-flash` 改为 `glm-4.6v-flash`，同步更新 `AiProviderConfigServiceImpl`、`AiUserKeyServiceImpl`、`AiPricing`。

结果：devtools 热加载没生效，日志仍显示旧模型名。

### 第三轮：base64 前缀问题

智谱官方 Base64 示例传的是**裸 base64 字符串**，不带 `data:image/png;base64,` 前缀。而代码里 `QuestionServiceImpl` 拼的是完整 data URL 格式，`AnalysisService` 原样传给 API。

修复：在 `callAiApiWithImage` 里根据 provider 类型（`glm`/`zhipu`）剥离 `data:image/...;base64,` 前缀，只传裸 base64。其他 provider（如 OpenAI）保留 data URL 格式。

### 第四轮：devtools 未生效

杀掉旧进程、重新 `mvn spring-boot:run` 后，新代码终于生效。日志确认：
- `model=glm-4.6v-flash`
- `imageDataPrefix=data:image/png;base64,...`（日志打印原始值）
- 实际发给 API 的是剥离前缀后的裸 base64

调用成功，返回 JSON 识别结果。

## 修改的文件

| 文件 | 改动 |
|------|------|
| `AnalysisService.java` | 消息结构、模型名、base64 前缀剥离、校验、脱敏日志、chatEndpoint 防重复追加、用量日志区分 vision/runtime |
| `AiProviderConfigServiceImpl.java` | 默认 vision_model 从 `glm-4v-flash` 改为 `glm-4.6v-flash` |
| `AiUserKeyServiceImpl.java` | 同上 |
| `AiPricing.java` | 新增 `glm-4.6v-flash` 价格条目 |

## 经验总结

### 1. 不同模型的 API 限制不同

GLM-4V 系列不支持 `system` role，只接受 `user` 和 `assistant`。通用 chat 模型（如 `glm-4.5-air`）支持 `system`。重构时不能假设所有模型都支持同样的消息结构。

### 2. Base64 图片格式因平台而异

- 智谱 GLM：传裸 base64（`iVBORw0KGgo...`）
- OpenAI：传 data URL（`data:image/png;base64,iVBORw0KGgo...`）

不能一刀切，需要按 provider 类型分别处理。

### 3. 模型名要跟平台实际可用的一致

官方文档列出的模型名（`glm-4v-flash`）不一定跟实际 API 可用的模型名（`glm-4.6v-flash`）一致。需要以实际调用成功的模型名为准。

### 4. Devtools 热加载不总是可靠

Spring Devtools 在修改复杂初始化逻辑（如 `new HashMap<>() {{ ... }}` 匿名内部类）时可能不触发重新加载。排查问题时应该先杀掉进程重新启动，而不是依赖热加载。

### 5. 脱敏日志是排查远程 API 问题的关键

日志里打印 `model`、`url`、`apiKey` 前 8 位、`imageDataPrefix` 前 50 字符、`contentTypes`，可以快速定位是哪个参数有问题，又不泄露密钥和完整图片数据。

### 6. 架构统一的代价

把图片识别从硬编码路径迁入统一密钥管理系统的过程中，不能简单地复用旧的硬编码参数。每一步都要对照目标平台的 API 文档验证：消息结构、模型名、图片格式、endpoint 路径。
